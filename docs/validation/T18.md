# Validation T18 — Séquences multiécrans et exercices de réalisation

15 novembre 2026. Statut : **T18 terminée et validée pour son périmètre**. La page SÉQUENCE propose le mode simultané/décalé, les six ordres possibles et un délai borné à 0…1 000 ms, par pas de 100 ms. Le trajet conserve sa succession obligatoire. Le guide reprend les situations de la section 5.4.6 de la spécification, avec les raccords manuels et l'exercice général → chanteur → solo → public. La limite de la longue sélection navigateur est explicitée ci-dessous ; la stabilité finale et les mesures matérielles restent à T19.

## Comportements et propriété des ressources

Le résumé réutilise le plan métier pour afficher l'ordre effectif et le total, en ignorant les écrans non ciblés ou déjà sur B. En décalé, chaque écran attend la fin du précédent et le délai. Le simultané ignore ordre et délai ; ces commandes y sont grisées. Le pupitre rétablit le choix 2D précédent après un trajet. Les réglages modifiés pendant un passage préparent uniquement la commande suivante ; la progression par écran provient de la commande capturée.

Les coupes décalées utilisent la transaction et les shaders 2D existants avec une progression par écran de 0 ou 1. Les sources initiales restent possédées et rendues jusqu'au commit global ; une annulation ou une panne tardive restaure aussi les écrans déjà passés sur B. Le plafond est de quatre sources vivantes, puis trois au plus au repos sans aperçu. Une coupe instantanée conserve le chemin du socle à trois sources. Le trajet partage sa seule caméra temporaire et respecte cinq sources au maximum. Aucun pool ni RTT de composition supplémentaire n'est créé.

## Recette navigateur

La commande finale sélectionne les effets 2D, aperçus, trajets et séquences :

```powershell
$env:PLAYWRIGHT_CHROMIUM_CHANNEL = 'chrome'
npm run test:e2e -- screenSequence.spec.ts transitions.spec.ts preview.spec.ts travelSource.spec.ts travelPreview.spec.ts --workers=1 --timeout=180000 --reporter=line
```

La longue sélection termine avec **53 réussites sur 54 en 17,6 minutes**. Le parcours d'aperçu au pupitre dépasse 180 secondes au démarrage, avant toute interaction. Sa trace montre la connexion Vite et la création WebGL2, sans erreur applicative explicite ; la cause du blocage n'est pas établie. Rejoué seul, **le même parcours réussit en 39,8 secondes**, sans modification du code de production ni du délai. Les 54 parcours distincts ont donc une exécution réussie, mais la longue sélection n'a pas été entièrement verte en une seule exécution. Ce blocage de démarrage reste à surveiller dans la recette de stabilité T19.

```powershell
npm run test:e2e -- preview.spec.ts --grep 'uses the spatial preview controls' --workers=1 --timeout=180000 --reporter=line
```

La sélection comprend aussi `graphicTransitions.spec.ts`, dont le nom correspond au filtre `transitions.spec.ts`. Le backend configuré est **Windows / Chrome / WebGL2 / ANGLE SwiftShader** ; ces tests ne mesurent pas le GPU matériel.

Les cinq nouveaux parcours couvrent :

- Les pixels de chaque écran pour les six ordres de coupes décalées, les cibles déjà sur B et une cible partielle inchangée ; les routes ne sont validées qu'à la fin et le flux final est partagé.
- L'annulation puis, séparément, la panne de shader après le premier fondu terminé et le deuxième en mélange ; toutes les images initiales et les compteurs de ressources sont restaurés, puis la reprise réussit. Les compteurs de dessins vérifient que les quatre sources continuent à rendre.
- L'exercice entièrement au pupitre physique : écran partagé, retour à la coupe, trois départs distincts, chanteur, délai et ordre effectifs, annulation après le centre, nouvel ordre, diffusion complète puis solo et public. Aucun appel à l'API de recette pour ce parcours.
- Le trajet sur deux cibles dans un ordre choisi, délai de 1 000 ms, attente sans déplacement d'image, réutilisation de la caméra temporaire sans accumulation, extrémités exactes et commit global avec la cible non concernée conservée.

Le scénario 19 enchaîne écran partagé puis séquence/annulation après le premier écran dans la même scène au pupitre, complété par les contrôles de pixels des deux fonctionnalités. La lecture de pixels inspecte les écrans successivement, car l'observateur de recette est une seule caméra partagée.

Après ajout explicite de l'écran partagé au début de ce parcours, sa réexécution isolée réussit en **56,7 secondes** :

```powershell
npm run test:e2e -- screenSequence.spec.ts --grep 'performs the multi-screen directing exercise' --workers=1 --timeout=180000 --reporter=line
```
